# Beta feedback

Owner: Gauthier Berth. Collect feedback through `support@lawrelay.be` and conversations with actual users. No feedback has been invented or pre-filled here.

Use targeted replies, not bulk outreach. Migadu Micro's [20 outgoing attempts per day](https://www.migadu.com/pricing/) are shared by verification, proposal notifications, support and alerts across the account. This is an infrastructure limit, not an invitation or registration cap; leave paid subscriptions disabled. Keep outgoing tests and repeat retries minimal. Failed mail jobs trigger the existing health-alert route, but SMTP alert delivery also depends on that shared quota.

## Ask about the actual attempt

- What were you trying to do: register, verify, post, respond, choose a colleague, or get help?
- Where did you get stuck, and what did you expect to happen?
- Did you finish? If not, what stopped you?
- What one change would make the next attempt easier?

Ask for the page, approximate time, preferred language, and browser only when useful. Do not request client names, case facts, documents, passwords, or confirmation links. Get permission before recording a conversation or retaining a screenshot; remove personal and confidential details from anything shared with developers.

## Record privately

Keep the source conversation in the restricted support mailbox or an operator-controlled private record, not in Git. Use this template:

| Status / review date | New / investigating / planned / fixed / closed |
| Follow-up result | What the user actually confirmed |

## Turn feedback into work

Review the records weekly while the beta is active. Prioritise failures to register or verify, inaccessible controls, missed notifications, and unclear assignment or response flows. Create a sanitised GitHub issue only when it describes the product problem without exposing a user or matter; leave identifying source evidence in the private record.

Track actual counts for registration, verified access, first assignment, first response, accepted proposal, and completed assignment. Record the observation period and denominator. Report user feedback and product events separately; do not treat an accepted proposal as a completed professional engagement or infer satisfaction from silence.

After a fix, test the affected flow, ask the reporting user whether it helped when contact is appropriate, and record the result. Real usage and repeat use remain unproven until actual users supply evidence. Platform pricing is [archived](../archive/pricing.md); focus on whether the service is useful.
